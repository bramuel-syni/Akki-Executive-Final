P R O D U C T   F E E D B A C K   ·   M E M O

Akki — Eight journey rewires.
Calibration based on the current production UI. Each journey with objective, output, and the specific rewire required.
This memo is product feedback after walking through the current production UI. It covers eight journeys — three major rewires (Documents Journal, Workspace, Cycle Manager), one feature redesign (Pulse), one foundational security guardrail (Roles & Company Navigation), and three surface-level corrections (Solva UI tiles, general UI styling, Chat with the two-pass method baked into the response pipeline). Each journey is presented with its objective, its output, the specific rewire required, open questions where PM judgement is needed, and what is deliberately out of scope.
The through-line across all eight items: the product is currently presenting too much architecture to the user. Surfaces are congested, journeys diverge into too many parallel paths, and capabilities are exposed before the user has reason to want them. The rewires below collapse paths, hide architecture by default, and surface the right thing at the right moment. Where I introduce elements not in my original walk-through notes, they exist only to close broken journeys — never to expand scope.
One operational note for the PM: the Chat section (Item 8) contains the canonical two-pass method prompt verbatim, plus a chat-adapted operational form, plus the trigger logic the engineering team needs. This is the single most consequential implementation requirement in the memo because it defines how the chat experience guards against fabrication on every user turn.

EXECUTIVE SUMMARY
# The through-line
The product currently exposes architecture where it should expose experience. Across the eight items below, the same failure mode appears: the user encounters Akki's internal structure (clusters, three-column layouts, parallel surfaces, multi-step navigation, dense tile grids) before they have any reason to engage with it. Senior people exit when the surface demands more attention than the moment justifies.
The rewires in this memo collapse the architecture in five concrete ways:
1.  Documents move from main-menu prominence to homepage button — surfaced when wanted, not always present.
2.  Workspace consolidates around a single drawer pattern — replacing three-column heavy layouts.
3.  Cycle Manager becomes a drafting engine with three managed objectives — replacing diffuse screen real estate with purposeful surface.
4.  Pulse adopts a known social-feed metaphor — Twitter-style, with filtering and engagement, replacing custom navigation.
5.  Chat applies the two-pass method on every turn — silent guardrail against fabrication, not visible architectural performance.
Two items are foundational guardrails that should ship before the rewires: Roles & Company Navigation (a security gap that must close), and the Chat reasoning discipline (the property that makes Akki safe to use).
## Priority and sequencing
Recommended sequencing for the build team:


ITEM 1
# Documents Journal
OBJECTIVE: Give the user one place to find and act on every document — uploaded externally or generated by Akki — without that surface dominating navigation.

OUTPUT: An indexed, searchable document repository the user reaches via a homepage button rather than a main-menu item, with a single drawer for any document opened.
## Current state
Documents Journal is a main-menu item taking permanent navigation real estate. Each document, when clicked, opens a three-column page that is heavy to scan and difficult to follow. The upload affordance takes excessive space.
## The rewire
Three connected changes:
1.  Move Documents Journal off the main menu. Replace the main-menu slot with whatever is more frequently accessed (PM judgement — see Open Questions).
2.  Add a homepage button labelled "All documents" with a document icon. Position it in the empty space marked on the homepage screenshot. The button takes the user to the Documents Journal page.
3.  Inside Documents Journal, move the upload and camera affordances into the title bar at reduced size. Keep them discoverable; don't let them dominate.
## Document detail — single drawer pattern
When a document is clicked, the current three-column page is replaced by a single drawer. Drawer content:
•  Drawer title = document name
•  Drawer body = Akki notes only (the substantive analysis the user came for)
•  The middle column from the current three-column page is hidden by default and accessible via an icon in the drawer title bar — same pattern as the marked-up empty space

All marker, tracking, and scoring features that exist on the current document detail surface remain — they migrate into the drawer rather than the three-column layout.
## The search property
Documents are indexed so they can be found by partial recall — "the doc was about provisioning compression" should surface the right document even when the user doesn't remember the filename. Treat this as an internal Google: search across document content, Akki notes, and metadata. Search is the primary discovery mechanism inside Documents Journal; browsing is secondary.
## Specific journey steps
1.  User on homepage clicks the "All documents" button
2.  Documents Journal page loads with title bar containing reduced-size upload and camera affordances
3.  User searches by name, content keyword, or topic — index returns matches across all documents
4.  User clicks a result — single drawer opens with Akki notes
5.  If user wants the structural detail previously in the middle column, they click the icon in the drawer title bar to surface it
6.  Markers, tracking, scoring features remain accessible within the drawer
## Open questions for PM
•  What replaces Documents Journal in the main menu slot? My instinct: nothing — collapse the menu by one item. PM to confirm.
•  On mobile, the drawer pattern needs a stacking decision. Drawer becomes full-screen modal? Or drawer becomes a new screen? PM to choose based on broader mobile pattern.
•  Should the homepage "All documents" button include a count badge ("All documents · 47")? Light addition that increases discoverability without congesting the surface. PM to decide.
## Out of scope
•  Document categorisation taxonomy beyond what indexing already supports
•  Document collaboration features (comments, mentions) — separate workstream
•  Bulk document operations — separate workstream


ITEM 2
# Workspace
OBJECTIVE: Make Workspace the surface where users improve the quality of their documents — generated by Akki or uploaded for company-specific precision context.

OUTPUT: Three resource types (Briefs, Decks, Reports) accessed through a single interaction pattern (drawer + action bar), with executive-quality output and the option to refine in chat after generation.
## Current state
Workspace has "Briefs," "Decks," and "Reports" as parallel listings, with "+Start a Brief / +Start a Deck / +Start a Report" CTAs. The relationship between Briefs (Akki's analysis) and Decks/Reports (output documents) is not explicit. Decks generated currently appear as outline versions rather than actual decks.
## The rewire
### Briefs — what they are
Briefs are Akki notes on aggregates. Three aggregate types:
1.  Cycle Board Pack — all documents sent to NEDs during a cycle, put together. E.g., Q4 2026 Board Pack.
2.  Cycle Minutes — all minutes from main board meetings in a cycle, put together. E.g., Q3 2026 Minutes.
3.  Cycle Board Committee Packs — all minutes, reports, and submissions from a specific committee in a cycle, put together. E.g., Audit Committee Q2 2026.

Each listing displays markers: date of the relevant meeting, number of documents in the aggregate, number of contributors. The Briefs section is a navigable index of these aggregates.
### The Brief drawer
When a user clicks an aggregate listing, a side drawer opens (~50% page width — adjustable to maintain system feel). Drawer content:
•  Title — name of the listing (e.g., "Q1 2026 Board Pack")
•  Topline — number of documents, contributors, period of collection
•  Notes — classified by topic, with citations to specific documents in the aggregate

The drawer is clean, lightweight, and easy to scan. Maintains the same discipline as the Documents Journal drawer pattern — one surface, one job.
### Action bar — five buttons
Replace the current "+Start a..." CTAs. The new action bar has five buttons:
1.  Export a Brief — user gives description, objective, scope; Akki generates; user gets download pin and downloads document. Document is executive-quality (well written, designed, organised). Output formats: docx / pptx / pdf per user preference.
2.  Export a Summary Deck — same flow, deck output.
3.  Export a Report — same flow, report output.
4.  Enhance my Deck — net-new feature. User uploads a deck they're working on. Provides context: objective, success criteria, what "done" looks like, what's missing. Akki analyses, scores, and provides an enhancement plan and concrete improvements. Underlying model applies the two-pass method (Solva on itself) to ensure no fictitious or assumptive output that would mislead the user.
5.  Enhance my Report — same journey as Enhance my Deck.

This is where everyone comes to check whether their presentations are solid. The Enhance buttons are the most distinctive value proposition in this section — they convert Workspace from a generation tool into a pre-board / pre-meeting quality-assurance surface.
### Decks and Reports — output listings
"Decks" lists every deck generated by Akki or uploaded for review. "Reports" same. User clicks a listing — current journey is preserved, but the output must be the actual deck/report (slide composition, document layout) rather than the outline placeholder it currently shows. Production quality should match what a senior person could take into a board meeting.
### Continue in chat
After a document is generated, the user can continue refining it in chat. Chat is aware of the document context and can edit, regenerate sections, or restructure based on natural-language instructions.
## Specific journey steps — Export
1.  User in Workspace clicks Export a Brief / Deck / Report
2.  Akki prompts for: description (what is this for), objective (what should it achieve), scope (what to include/exclude)
3.  User provides; Akki generates
4.  User receives download pin; downloads in chosen format
5.  Document is executive quality — production composition, not an outline
6.  User can return to chat to refine; chat retains document context
## Specific journey steps — Enhance
1.  User in Workspace clicks Enhance my Deck or Enhance my Report
2.  User uploads existing document
3.  Akki prompts for: objective (what should this deck/report do), success criteria (what does a win look like)
4.  Akki applies two-pass method on itself before producing analysis (no fabrication, no assumed gaps)
5.  Akki returns: a score, what's working, what's missing, an enhancement plan, and concrete suggested improvements
6.  User can ask Akki to apply the suggested improvements directly, request specific changes, or take the analysis offline
## Open questions for PM
•  Document quality bar for Export. "Executive-quality" means production composition with typography, structure, and visual treatment — not an outline. The PM should specify the rendering pipeline (template engine, design tokens, output validation). Without this, the Export risks producing the same outline-quality output the current Decks listing already produces.
•  Enhance scoring rubric. What dimensions does the Enhance feature score on? PM judgement, but I'd suggest: structural integrity, evidence support, audience fit, narrative coherence, presentation polish. PM to confirm.
•  Continue-in-chat document context. Chat needs to know which document is being refined. PM to specify the handoff (chat opens with document attached as context, or chat references document by ID, or other).
## Out of scope
•  Real-time collaboration on documents in Workspace
•  Version history beyond what document storage already provides
•  Document templates library — separate workstream


ITEM 3
# Cycle Manager (Executive flow)
OBJECTIVE: Give executives a drafting engine that compresses the cycle of operator review, draft answers, and consolidation into a single managed surface — replacing the current diffuse compilation process across email, files, and notes.

OUTPUT: A cycle agenda with a managed team, real-time scoring of incoming contributions, an audit-grade readiness dashboard, and a final consolidated draft compilation the executive can submit with confidence.
Note on scope
This memo covers the Executive flow only. The NED-side Cycle Manager (catch-up and cycle monitoring) is a related but distinct journey. PM to scope NED-side as a follow-on workstream after Executive flow ships.
## Current state
Cycle Manager exists conceptually but is currently a passive structure that displays cycle information without actively driving the executive's compilation work. Executives still compile board materials in their own tooling — email threads, shared drives, manually consolidated notes.
## The rewire
### Cycle Manager as a drafting engine
Rebuild Cycle Manager around three executive objectives, each with a manager function:
1.  Operators review — Akki tracks incoming material from team members, scores it for relevance, fullness, readiness.
2.  Draft answers — Akki monitors open questions from prior minutes, reports, and Pulse signals; surfaces what needs response.
3.  Consolidate the material the executive plans to share with the board — Akki produces the compilation when the readiness scoreboard says it's ready.
### Setting up the cycle
The user sets a reporting agenda. Akki recommends defaults based on the role and company. Agenda options:
•  Main board reporting cycle
•  Monthly updates
•  Committee reports (audit, risk, nominations, etc.)
•  Response to questions / open items from prior cycles

User builds the team around the agenda — adding direct reports, functional leads, advisors — and describes each linked team member's contribution to Akki. "Sarah owns the credit risk update. James contributes the cyber posture section. The CFO's office handles the finance update."
### How Akki tracks and scores
Once the agenda and team are in place, Akki:
•  Tracks incoming information from each team member (uploaded documents, email contributions if forwarded, chat-shared content)
•  Scores each contribution on three dimensions: relevance (does this fit the agenda item it's mapped to), fullness (is this complete or partial), readiness (is this draft-ready or still in development)
•  Monitors open questions surfaced from previous minutes, reports, or Pulse signals
•  Maintains a readiness scoreboard showing per-agenda-item completeness, pending actions, and persons responsible
### The follow-up function — "Akki for Bram"
On user approval, Akki can make follow-ups on the user's behalf — "Akki for Bram" — and receive documents through email the same way the user would. This closes the loop on chasing contributions without requiring the executive to do the chasing personally.
Boundary on follow-ups
Akki sends follow-ups only on explicit user approval per follow-up. No autonomous mass follow-ups. The executive sees what Akki proposes to send before it goes out — preserves the voice, preserves the relationship, preserves accountability.
### The summary storyline
Akki provides a summary storyline that helps the user decide whether the compilation is ready. The storyline names: where readiness scores are strong, where they're weak, what's still pending, and what the risk profile of submitting now would be. The user reads the storyline and decides for themselves against the scoreboard.
### Draft Compilation Output
The user can click "Draft Compilation Output" at any time — Akki does not gate this. The executive's judgement determines when the compilation is ready. Akki's role is to surface the readiness signal, not to decide for the user.
## Specific journey steps
1.  User opens Cycle Manager
2.  User selects or accepts the recommended reporting agenda
3.  User builds the team — adds members, describes each member's contribution to Akki
4.  Akki begins tracking incoming material as team members contribute
5.  User monitors the readiness scoreboard; reads Akki's summary storyline
6.  User approves Akki to send follow-ups where contributions are missing or thin
7.  When user is satisfied, user clicks Draft Compilation Output
8.  Akki produces the compiled draft — executive quality, citation-ready, voiced for the user
## Open questions for PM
•  Email integration depth. "Akki for Bram" follow-ups — does this require email account integration (OAuth to Gmail/Outlook), or does it work through a forwarding alias ("forward replies to akki+bram@syni.ai")? PM judgement based on engineering complexity vs user friction.
•  Scoring algorithm transparency. Should users see why a contribution was scored as it was? My instinct: yes, with a tooltip showing the three scoring dimensions. Avoids black-box frustration.
•  NED-side Cycle Manager. As noted in scope: separate workstream. PM to size and sequence.
## Out of scope
•  NED-side Cycle Manager (catch-up and monitoring) — separate workstream
•  Calendar integration for scheduling cycle meetings — separate workstream
•  Approval workflows beyond follow-up sends — separate workstream


ITEM 4
# Pulse
OBJECTIVE: Surface signals (risks, opportunities, recommendations) in a familiar social-feed format that invites engagement and easy filtering — replacing the custom navigation that currently underuses Pulse's substantive content.

OUTPUT: A Twitter-style feed of signals with text, graphs, or visualisers attached, filterable by category and freshness, with comment and share affordances that let users engage rather than just observe.
## Current state
Pulse currently surfaces signals through a custom interface that requires the user to learn its navigation. Engagement is low because the format doesn't invite it.
## The rewire
### Format — social feed metaphor
Adopt the Twitter-style feed pattern. Each signal is a thread:
•  Some threads are text-only — a risk or opportunity named in prose, with a recommendation
•  Some threads have graphs or visualisers attached — pattern data the signal depends on
•  All threads carry the signal type tag (Risk / Opportunity / Recommendation) and a freshness indicator (new / critical / old-but-unresolved / nice-to-look-into / for-tracking-purposes)
### Filtering
Two filter dimensions, simple to engage:
1.  Type — Risks / Opportunities / Recommendations / All
2.  Freshness — New / Critical / Old-but-unresolved / Nice-to-look-into / For-tracking-purposes

The freshness filter is the more consequential one. The user's actual question on opening Pulse is usually "what's new and what matters," not "show me all risks." Default view: "new" + "critical" combined.
### Engagement
Standard social engagement primitives, calibrated for executive use:
•  Comment — user can comment on a signal (private to them and Akki, not public)
•  Share — user can share a signal with a colleague (in-product or by email)
•  Save — user can save a signal for later reference
•  Mark resolved — user can mark a signal as resolved, removing it from active filters
•  Take to Solva — direct path from a signal into a Solva session with that signal as the framing
### Recommendations on signals
Each signal carries an associated recommendation — what Akki suggests doing next. The recommendation is the action layer; the signal itself is the surfacing layer. Together they convert an observation into a starting point for action.
## Specific journey steps
1.  User opens Pulse
2.  Default view shows new + critical signals as a feed
3.  User scrolls; engages with signals (comment, share, save, mark resolved, or take to Solva)
4.  User filters by type or freshness as needed
5.  Saved signals appear in a separate tab for later review
## Open questions for PM
•  Comment privacy model. My instinct: comments are private between user and Akki. PM to confirm — alternative is shared comments with co-users on the same company.
•  Share mechanism. In-product share (to another Akki user) versus external share (email link). PM to scope which ships first.
•  Visualiser library. Which visualiser types are needed? Probably: line chart, bar chart, simple table. PM to scope based on signal types in production.
## Out of scope
•  Public commenting / industry-wide discussion threads
•  Signal authoring by users (signals are Akki-generated, not user-generated)
•  Push notification preferences for new signals — separate workstream


ITEM 5 — SECURITY GUARDRAIL
# Roles & Company Navigation
OBJECTIVE: Enforce role boundaries when users move between companies — preventing the security gap where a user retains executive privileges across companies they don't have executive role in.

OUTPUT: Role binding to company. A user logged in as Executive at Company A who switches to Company B (where they are NED) loses executive privileges and gains only the NED-role functions assigned to them at Company B. Notification on switch. No silent privilege carryover.
This is a security item — ship before any of the rewires above
The current behaviour permits a user to switch companies while retaining the role they had in the previous company. If a user is Executive at Ubora and NED at Mara, they can currently access Mara's executive functions because the system did not rebind the role on company switch. This is a major security function and should be the first item the team ships from this memo.
## Current state
Company switching does not enforce role rebinding. Privileges from the prior company persist in some flows, exposing executive-level functions to users whose role at the current company is NED, External Company Secretary, or another less-privileged role.
## The rewire
### Role binding
Roles are bound to (user, company) pairs — not to user accounts globally. A user may be Executive at Ubora, NED at Mara, External Company Secretary at Sendwa. The system enforces:
1.  Role privileges are determined per (user, company). Switching company switches the active role to the role assigned at the destination company.
2.  If a user has no role at a destination company, they cannot enter — the company does not appear in their company switcher.
3.  Role privilege escalation across companies is impossible by design. A user cannot carry executive-only views, write privileges, or delete privileges from one company into another.
### The notification on switch
When a user switches company, the system displays a clear notification:
Switch notification copy
You're now in [Company B] as [Role at Company B]. Your access here is limited to what [Role] is permitted to do at [Company B]. To return to [Company A] as [Role at Company A], use the company switcher.

The notification confirms the role binding has occurred and reminds the user how to switch back. This is intentionally a momentary modal, not a passive header — users should consciously acknowledge the role context shift.
### Audit
Every company switch and every privilege check is logged. The audit log is accessible to administrators of each company independently. This is the audit log this memo's item 8 (Chat) also uses — they are the same architectural component.
## Specific journey steps
1.  User uses company switcher to move from Company A to Company B
2.  System checks: does user have a role at Company B? If no, switcher hides Company B.
3.  If yes, system rebinds session role to the role at Company B
4.  All privilege checks for the active session now use the new role
5.  Switch notification is displayed; user acknowledges and continues
6.  All session activity is logged with (user, company, role) triples
## Open questions for PM
•  Edge case — user is removed from a company while logged in. Behaviour: next privilege check fails; user is forced to re-authenticate / re-select company. PM to confirm UX of this transition.
•  Edge case — user is granted a new role at a company while logged in. Behaviour: company appears in switcher on next refresh. PM to decide whether to push notify.
•  Multi-tab behaviour. If user has Akki open in two tabs at different companies, what happens on a privilege-relevant action? My instinct: each tab is its own session; actions execute in their tab's company context. PM to confirm.
## Out of scope
•  Role granularity beyond Executive / NED / Company Secretary / etc. — separate workstream
•  Company-to-company data sharing or visibility — separate workstream
•  SSO/IAM integration with corporate directories — separate workstream (Enterprise tier)

ITEM 7
# General UI styling consistency
OBJECTIVE: Establish a single content-width pattern across the product, replacing the current inconsistency where some pages populate content in the middle and others spread end-to-end.

OUTPUT: A defined max-content-width applied consistently across all pages, with the same page padding rules, the same vertical rhythm, and the same alignment to design tokens.
## Current state
Some pages constrain content to a centred max-width column. Others spread content end-to-end. The inconsistency makes the product feel architecturally undecided and undermines the editorial restraint the design language is built around.
## The rewire
Establish three page-width patterns and apply them consistently:
1.  Single-column reading width — 760px max, centred. Used for: editorial content, Solva flow, Documents Journal drawer body, Brief drawer body, single-column flows generally.
2.  Two-column workspace width — 1200px max, centred. Used for: Workspace listings + drawer combined, Cycle Manager dashboards, Pulse feed.
3.  Full-width — used only for: data-heavy tables, comparison grids, Cycle Manager scoreboards where breadth is needed.

Most pages should use pattern 1 or 2. Full-width should be the exception, not the default. The discipline is restraint — most product surfaces don't need the breadth they're currently getting.
## Specific journey steps
No user-facing journey change. This is a design system pass that brings every page into alignment with the three patterns above.
## Open questions for PM
•  Page-by-page audit. PM should walk every page and tag which pattern applies. Send the inventory back for review before the design system pass.
•  Design tokens. The pattern widths should live in the design system tokens. PM to confirm tokens exist or need to be added.
## Out of scope
•  Visual redesign of components — this is layout consistency, not redesign
•  Mobile-specific patterns beyond what responsive rules already specify


ITEM 8 — FOUNDATIONAL QUALITY PROPERTY
# Chat — production experience with two-pass method baked in
OBJECTIVE: Match Claude's chat production quality (streaming, document generation, in-conversation refinement) AND apply the two-pass reasoning method silently before every response — guarding the user against fabrication and the LLM against misdirection.

OUTPUT: A chat experience where responses stream rather than dump, documents can be generated in-flow, and every response is preceded by a silent background reasoning pass that evaluates tension, contradiction, assumption, and framing limitations before producing output.
Why this is foundational
The two-pass discipline is what makes Akki safe to give institutional material to. If chat produces fluent-but-unsound output (the default LLM failure mode), every other safety property of the product is undermined. This item is P0 alongside the security guardrail in Item 5.
## Current state
Chat does not match the production experience users expect from Claude or ChatGPT in 2026. Responses arrive as completed dumps rather than streams. Document generation in-chat is limited. There is no visible discipline against fabrication on substantive turns.
## The rewire — production experience
Bring chat to parity with Claude's production UX:
•  Streaming responses — token-level, not response-level
•  Document generation in-conversation — the user can ask for a deck, document, or report and receive it without leaving the chat
•  File attachment in chat — user can attach documents for analysis
•  Conversation history with search and resume
•  Inline rendering of tables, code blocks, and markdown formatting
•  Continue refining a generated document — the chat retains document context for follow-up edits
## The rewire — two-pass method baked into every response
This is the substantive content from the broader two-pass methodology document. Inside chat, the method runs in the background on every user turn — the user does not see a visible Pass 1 / Pass 2 four-layer breakdown before their response (that would make chat unusable). Instead, the method runs silently and shapes the response cadence.
### The canonical two-pass method prompt
This is the canonical prompt from the broader methodology document. It applies to one-shot strategic deliverable production (decks, briefs, documents) where the visible Pass 1 reasoning is desired:
CANONICAL TWO-PASS METHOD PROMPT — paste verbatim

Operate under the two-pass method:

PASS 1 — SOLVE. Apply the four-layer reasoning architecture to the work itself before producing.
- Layer 1 (Surface): Generate 5-7 candidate framings for the task. Each substantively different.
- Layer 2 (Depth): Triangulate against context. Detect tensions and tag severity (CRITICAL / MATERIAL / MINOR).
- Layer 3 (Synthesis): Probability-weight the candidates with confidence intervals. Run sensitivity analysis. Refusal-check: do you have enough to weight scenarios honestly? If not, ask for more before proceeding. Select the winner.
- Layer 4 (Reflection): Three questions — what would change my mind? What's the explanation in six months if I got this wrong? What am I disappointed by?

PASS 2 — BUILD. Once Pass 1 has selected, build the deliverable.
- Honour Pass 1's positioning fully. Do not hedge into other scenarios.
- Apply operating preferences without negotiation.
- Validate the build against Pass 1's implicit acceptance criteria.

OPERATING PREFERENCES:
- No glazing. Stress-test before validating. Lead with what is wrong or missing.
- Direct and concise. First sentence is the substantive answer.
- The Economist test, senior peer test, restraint test must pass.
- Banned words: leverage (verb), empower, AI-powered, insights (noun), dashboard, game-changer, revolutionary, cutting-edge, disrupt, unlock, supercharge, seamless, frictionless, all under one roof, transform (generic), synergy.
- If production reveals Pass 1 was wrong, surface it — don't push through.

When you receive a task, begin with Pass 1 visibly. Show your candidate generation, your triangulation, your weighting, your selection, your reflection. Then proceed to Pass 2.

### The chat-adapted operational form
Inside chat, the method runs in the background — on every substantive turn — without the user seeing the four-layer breakdown. This is the chat-adapted form:
CHAT-ADAPTED FORM — applies on every substantive user turn, silently

Before responding to the user, evaluate four things in the background:

1. TENSION. Is the user's framing in tension with evidence I can see? With prior conversation? With what they said earlier in this same conversation? Surface the tension only if material.

2. CONTRADICTION. Is what the user is saying internally contradictory, or does it contradict prior context I have? If yes, name it gently.

3. ASSUMPTION. What is the user assuming that may not hold? Is the assumption load-bearing for their framing? If load-bearing and questionable, name it.

4. FRAMING LIMITATION. Is the user asking the right question? Or is there a question underneath theirs that would produce a more useful answer? If yes, briefly offer the reframe before answering the original.

Then respond. The four checks happen silently. The response surfaces them only when material — never as a performance of process. If all four pass cleanly, just answer.

Apply the operating preferences from the canonical method:
- No glazing. Don't open with affirmation phrases.
- Lead with the substantive answer in the first sentence.
- If evidence is thin, name it; do not fabricate to look helpful.
- Banned words apply (leverage, empower, AI-powered, insights as noun, etc.).

The framework's job is to guard the user against fabrication and the LLM against misdirection. Apply it on every substantive turn.

### Trigger logic — when to apply the method
Not every turn warrants the method. The chat needs trigger logic to scale application based on turn substance:
•  Trivial conversational turn ("thanks," "got it," "okay") — no method, just the natural response
•  Light substantive turn ("can you summarise this?" "what time was the meeting?") — operating preferences apply (no glazing, direct first sentence) but the four-check evaluation can be brief
•  Substantive analytical turn ("what should I do about X?" "is this strategy sound?") — full four-check evaluation in the background; response surfaces what's material
•  Strategic deliverable turn ("draft me a deck on X," "write me a position paper on Y") — full canonical two-pass method, with visible Pass 1 reasoning if the user asked for it explicitly, silent if they did not
### Refusal triggering
Critical implementation requirement: when the four-check evaluation reveals that responding honestly requires evidence the user has not provided, the chat should refuse to fabricate and ask for what's missing. This matches the refusal logic in Solva and Work Studio. Specifically:
•  If the user asks for analysis on something where the input is too thin, chat says: "I can give you candidate framings, but I don't have enough to weight them honestly. What would help: [specific evidence the user could provide]."
•  If the user asks chat to draft a claim that cannot be sourced from attached materials, chat says: "This claim isn't supported by what I can see. We'd need [specific source] to include it."
•  If the user is asking a question whose answer requires assumptions that materially affect the response, chat names the assumptions before answering.
## Specific journey steps
1.  User sends a message in chat
2.  System classifies turn substance (trivial / light substantive / substantive analytical / strategic deliverable)
3.  If trivial: respond normally
4.  If light or above: run the four-check evaluation in the background (tension, contradiction, assumption, framing limitation)
5.  If checks pass cleanly: respond directly
6.  If checks surface something material: surface it briefly before or in the response
7.  If evidence required for honest response is missing: refuse to fabricate; ask for what's needed
8.  Stream the response token-level
9.  If the user asked for a document: generate it in-flow with continue-refine support
